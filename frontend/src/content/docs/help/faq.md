# 排错导航

先分清：是模型 API 调用失败，还是网站登录、充值或 VIP 操作失败。同一个 HTTP 状态，在不同入口可能代表不同问题。

## 三步定位

1. **记录原始响应。** 保存状态码、错误正文中的 `code` / `type` / `message` / `reason`，以及响应提供的请求 ID。
2. **判断错误发生位置。** 区分客户端网络、网关鉴权与额度、模型上游，避免反复换密钥或重复充值。
3. **选取对应方案。** 修改一个因素后用小请求验证，再核对记录，不进行大量并发重试。

## 常见误判

- **401 不只是拼错密钥。** 本项目也会用 401 表示密钥停用或关联账户不可用。
- **403 不一定缺少 VIP。** 密钥过期、余额不足、IP 限制和分组失效都可能触发。
- **429 不一定只是 RPM。** 并发、排队、密钥预算额度、平台周期额度和上游限流都需要分别判断。
- **502 不一定是本地网络。** 上游认证失败也可能映射为 502，不应因此要求用户更换有效密钥。
- **HTTP 200 不保证生成成功。** 已启动的流式响应可能在后续事件中返回错误。

这些说明依据当前项目处理逻辑。不同协议、客户端和代理层可能改变错误包装，应结合正文，而不是只看一个数字。

## 重试原则

参数、鉴权、权限和预算额度问题，应先修正配置或处理限制。临时网络和上游故障可有限次数退避重试；有 `Retry-After` 时尊重该等待时间。

流式中断或支付状态不明确时，先核对记录，避免重复调用或重复付款。反馈问题前请遵循 [安全与隐私底线](/docs?cat=about&page=security)。
