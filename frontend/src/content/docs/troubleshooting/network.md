# 网络、超时与流式异常

没有 HTTP 状态，和服务器明确返回错误，是两种不同问题。先查看客户端是否真正收到响应。

## Network Error 或状态 0

网站请求未收到 HTTP 响应时，项目会显示类似 `Network error. Please check your connection.`，状态可能为 0。这不是服务器返回的 HTTP 0。

| 检查顺序 | 处理方式 |
| --- | --- |
| 地址与 DNS | 确认公布的域名可访问，没有空格或拼写错误 |
| 代理与网络 | 核对客户端是否使用了预期代理，是否只有该应用无法连接 |
| TLS / 证书 | 检查系统时间和证书信任，不关闭证书验证、不忽略安全警告 |
| 浏览器跨域或拦截 | 检查浏览器网络面板、扩展与应用部署方式；不要把密钥暴露到网页前端测试 |
| 请求是否取消 | 区分用户主动停止、页面关闭与连接失败 |

如果请求没有到达平台，就可能没有平台侧记录。不能仅根据记录为空认定故障已解决。

## 超时与等待过长

使用同一密钥、同一模型发送短请求，排除过长上下文、大文件和高并发。比较客户端超时、代理等待与模型响应时间，不把等待时间无限调大作为唯一方案。

超时后先检查使用记录和异步任务状态。原请求可能已经执行或产生部分输出，重新调用可能再次计费。

## HTTP 200 中的错误事件

流式连接启动后，HTTP 状态可能已固定为 200，后续仍能通过 SSE 错误事件或 Responses 失败事件告知异常。项目包含此类流式错误处理。

客户端应解析所用协议的事件，而不是只检查 HTTP 200；也不能把 SSE 数据当作普通 JSON 一次性读取。出现断流时，保存脱敏后的错误事件与时间。

## 断流、没有最终回复或工具调用失败

1. 核对客户端、模型和分组使用的是同一协议。
2. 检查客户端或代理是否中止长连接，是否存在并发重试。
3. 查看最终事件与错误正文，不只看最后一段文本。
4. 进入使用记录核对是否存在部分用量；工具调用、附件等高级能力应按当前渠道支持情况确认。

## 何时重试

临时网络或上游异常可以有限次数退避重试。参数、密钥、权限和明确预算限制应先处理原因；流式或异步任务不明确时，先查记录，避免重复执行。
