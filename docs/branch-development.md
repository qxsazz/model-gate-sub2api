# 分支开发与发布规范

本仓库长期维护 `main` 和 `staging`。一个需求最多使用一个临时分支；同一需求后续的修复、测试、主题调整和文档都继续在原分支上完成。

## 分支用途

| 分支 | 用途 | 保留时间 |
| --- | --- | --- |
| `main` | 已通过 PR 的生产代码；生产部署仍需执行发布流程 | 长期 |
| `staging` | 集成和测试；直接 push 会自动部署测试站点 | 长期 |
| `feat/<主题>`、`fix/<主题>` | 确实需要隔离或并行开发的功能、修复 | 完成合并后删除 |
| `upgrade/<官方版本>` | 上游升级，集中处理定制差异与回归 | 发布后删除 |
| `docs/<主题>`、`hotfix/<主题>` | 独立文档任务、生产紧急修复 | 合并并同步后删除 |

不用为“测试一次”“再改一点”“准备上线”增加 `-test`、`-final`、`-v2` 等分支。已有任务分支适合继续工作时直接复用。正常生产晋级使用 `staging → main` PR；只有需要冻结发布内容且 staging 还在接收别的工作时才建立临时 release 分支。

## 开始任务

```sh
git status --short
git fetch origin --prune
git branch -vv
git worktree list
gh pr list --repo qxsazz/model-gate-sub2api --state open
```

先确认是否已有同一需求的分支/PR，以及工作区是否有其他人的改动。不要在未检查的工作区 reset、强制切换或覆盖文件。

- 小型串行修改：在干净的本地 `staging` 上同步远程，修改并完成验证，再直接 push 到 `staging`。
- 较大功能、上游升级、并行任务：从最新 `origin/staging` 建立一个短期分支。后续请求继续复用，先通过候选提交的 CI 再合入 staging。
- 若生产存在尚未回同步的修复，先把 `main` 合回 `staging`，再继续开发。共享分支不 rebase、不强推改写历史。

## 测试环境

测试环境允许直接推送，不要求 PR。推送前检查 diff，运行与改动相关的验证；较大改动先在任务分支通过完整 CI。仓库现有检查包括：

- `CI`：后端单元/集成测试、golangci-lint、部署脚本检查。
- `Frontend CI`：前端 lint、类型、翻译、测试、构建，以及画布测试/构建。
- `Security Scan`：后端、前端和画布依赖检查。

按提交 SHA 核验结果，不能拿旧提交的绿色状态替代新代码。通过后将任务分支合入 `staging` 并直接推送；以 `Deploy Staging` 成功、站点健康和相关业务验收作为测试部署完成的依据。不要把“push 成功”当成“部署完成”。

## 生产发布

1. 固定本次已验收的 staging SHA，确认 CI、安全扫描、测试部署及相关业务验收通过。
2. 创建或复用面向 `main` 的 PR，说明问题、最终变化、验证结果和数据库迁移。合入使用 **merge commit**，保留上游和 staging 的提交历史。
3. 满足实际分支规则的检查/审核后合并。用户已明确授权发布时不重复询问。
4. 在 `main` 执行 `Deploy Production`，`source_sha` 填已验收的 staging SHA，`confirm` 填 `DEPLOY`。此流程提升同一个镜像 digest，不重新构建生产镜像。
5. 核验生产数据库备份、实际镜像、健康状态、版本及相关功能。发布脚本在失败时尝试恢复旧应用镜像；数据库迁移是否可回退必须单独评估。
6. 将 `main` 同步回 `staging`，优先快进，避免下一次重复冲突。清理已经完成的临时分支。

```sh
verified_sha='填写已验收的40位提交SHA'
gh workflow run deploy-production.yml \
  --repo qxsazz/model-gate-sub2api --ref main \
  -f "source_sha=$verified_sha" -f confirm=DEPLOY
```

只有文档/协作说明比已验收 SHA 多的发布候选，可以复用原镜像，但必须逐项确认应用、依赖、迁移和镜像构建输入完全一致。部署配置有变化时单独验证配置。Bot 在生产默认关闭；启用前提供独立的生产客户端、Bot 实例和群范围，不复用测试凭据。

## 清理分支

发布后进行一次清理，不持续积累旧功能、旧升级或旧发布分支。

1. 保存分支名与 tip SHA 的清单，确认没有打开的 PR 和未提交的工作。
2. `git merge-base --is-ancestor <分支tip> origin/main` 成功的已完成分支可以删除，提交历史仍保存在 main。
3. 因 cherry-pick 而不满足祖先判断的分支，用 `git cherry` 和实际 diff 核对。确认等价提交已进入主线后再删除。
4. 有独立提交的分支逐项判断；未确认用途的代码保留并记录原因，不能按分支旧或名字相似直接删除。
5. 删除远程分支前再次核对 tip SHA，防止删除期间有人新增提交。随后清理本地已合并分支和失效的远程跟踪引用。
6. 工作树中仍有未提交/未跟踪文件的目录保留；不要为删除分支而丢弃工作区文件。

确认已被替代的旧实现、一次性排障分支如仍需留存，可用单独的归档合并保留其提交父链，并在合并说明中记录原因；归档必须核对树完全不变，不能把过期脚本或旧代码重新部署。未确认是否仍在开发的分支不适用这一处理。

生产紧急修复从最新 `main` 开始，通过 PR 发布后及时合回 `staging`。长期回溯依靠 main 的提交历史和发布记录，不为每次操作再创建一个永久备份分支。
