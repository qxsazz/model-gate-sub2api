# 网关恢复压力测试报告

本报告记录 `0.2.18-mg.3` 的压力测试。后续 `0.2.18-mg.4` 将恢复限制为异常后激活，尤其修正了正常账号排队误用恢复等待预算的问题；因此本报告的满载结果不能直接代表修正后的正常路径。

日期：2026-10-23（America/New_York）。代码：`f4bdb7dd48285263a0c1ee7582cff4f469fb76bb`，版本 `0.2.18-mg.3`。

恢复能提高可恢复故障的成功率，本轮没有发现整体服务被恢复队列拖死；但满载下仍有长时间等待后失败、账号排队不均、取消后在途连接继续占用，以及恢复窗口不是端到端硬超时这几项风险。适合继续测试，不能凭本轮结果承诺生产用户几乎不报错。

## 环境与方法

- 独立本地网关，真实 PostgreSQL 18、Redis 8.4、真实 API Key 认证、用户/账号并发与 OpenAI 高级调度；160 个合成用户，6 个分组，20 个合成账号。数据库和缓存为专用临时容器。
- 主矩阵 4,300 次请求，补充开关对照、预算与取消探针后累计记录 4357 次请求；最大客户端并发 128。主路径 `/v1/chat/completions`，默认模拟上游处理时间 40ms。
- 网关 `GOMAXPROCS=2`、Go 内存软限制 512MiB；PostgreSQL 1.5GiB / 2 CPU，数据库池 20/10；Redis 128MiB。仅使用本地合成价格与虚拟余额，不调用付费生成。
- 主矩阵使用恢复默认值：300 秒准入窗口、120 秒累计等待、12 次失败上限，等待准入上限 256/实例、64/分组、2/用户。高级调度开启，订阅账号优先关闭，其余评分使用默认值。
- 真实测试站、生产站及真实上游没有承受本次压力。

## 关键发现

1. **可恢复故障确实被网关消化。** 部分来源持续 503 时 512/512 成功，上游调用 530 次（约 1.04 倍）；部分来源 401 时 256/256 成功，上游调用 447 次（约 1.75 倍，池模式下可发生同号重试）。
2. **全故障会等很久，仍然失败。** 全部来源持续 503 时 96/96 最终返回 503，P95 约 121.5 秒，单请求最大上游调用 5 次，没有无限换号。等待上限不意味着一定能恢复。
3. **满载存在排队效率问题。** 两个账号各 1 槽、每次 3 秒、96 并发：54 成功、32 返回 503、10 等约 120 秒后返回 429。两个账号实际命中 39/15 次，存在明显不均；当前账号等待计划会固定等待所选账号，建议验证分段等待后重新选号，保留请求总预算及会话绑定边界。此结果不能简单等同于正常生产流量的失败率。
4. **健康分组未被整体拖死。** 满载和全故障期间，各并行发送 512 个健康请求，均全部成功；P95 分别约 0.355 秒、0.463 秒，对照 32 并发健康基线约 0.356 秒。相同用户同时有故障请求时，另一个健康请求也在约 160ms 完成；这不代表所有用户并发配置都已覆盖。
5. **取消后的队列与实际连接不是同一层。** 0.3 秒取消后 0.5 秒复测，Redis 账号槽位、用户槽位、等待计数均为 0，但模拟上游仍有 2 个在途调用。后续请求取得 Redis 槽位后，仍等待 HTTP 连接，P95 约 3.208 秒；完成后计数再归零。主矩阵 15 秒慢上游场景的后续请求 P95 约 16.1 秒。没有发现 Redis 槽位永久泄漏，但不能宣称取消会立即释放所有实际资源。代码中 `sendCCUpstreamRequest` 使用分离的上游 context，账号隔离连接池 `MaxConnsPerHost` 又与账号并发数对应，与该现象一致。
6. **300 秒是恢复准入预算，不是整个调用的硬截止。** 用同一代码缩放为 3 秒恢复窗口，先短暂无号，再启动一个 5 秒上游调用，总耗时约 6.33 秒仍成功。此项属于缩放机制探针，不是“默认 300 秒已实测超时”的数据。
7. **明确原因仍及时返回。** 白名单外模型 32/32 返回 404，P95 约 50ms，未调用上游；余额不足探针约 6ms 返回 403，未调用上游。

## 资源与无效样本

主矩阵网关采样峰值 RSS 185.65MiB，采样峰值 CPU 61.6%（psutil 口径，100% 为单核）。该采样不能替代长时间稳定性测试，也不能把模拟上游下的 RPS 当作生产容量。

第一轮把 PostgreSQL 限为 384MiB 且使用默认 256 连接池，数据库发生 1 次 cgroup OOM kill 和自恢复，出现认证/错误记录 500。该轮数据保存在 `invalid-db-limit/`，未混入主矩阵。调整为 1.5GiB、池 20/10 后重跑，没有再观察到数据库 OOM。这也是部署资源和数据库连接池需要匹配的证据。

## 建议优先级与覆盖限制

- 优先厘清取消后的上游排空、连接池占用及可观测性，避免 Redis 显示空闲而请求仍等待实际连接。保留准确用量结算，不能简单提前释放所有资源。
- 仅在已进入异常恢复的可安全切号请求中，评估“短段账号等待 → 重新交给高级调度”；正常请求继续使用原有 WaitPlan。上游绑定和已输出内容的请求继续遵守原有边界。
- 明确恢复阶段、单次调用、客户端与代理的超时关系，网页提示恢复状态，避免重复提交。
- 本轮未覆盖 WebSocket 长会话压力、Gemini 请求压力、真实 CDN/反向代理超时、跨实例共享队列、公平性或全站 256 等待名额饱和。没有测试真实付费上游、真实扣费正确性或长期内存稳定性。

## mg.4：正常调度与异常恢复分开验证

代码核对发现 mg.3 只凭恢复 context 存在就覆盖普通账号 WaitPlan，且 WebSocket 的正常抢槽也会启用恢复等待。mg.4 改为异常后才激活：正常请求沿用原有选号、评分、粘性、并发队列及等待超时；确认可恢复故障或诊断发现临时不可用候选后，才开始恢复窗口。成功完成 WebSocket 一轮后再次回到未激活状态。

2026-10-23 使用同一 mg.4 二进制、真实高级调度、PostgreSQL/Redis 和模拟上游，以关闭/开启/开启/关闭顺序重启独立进程对照。正常场景预热 Key，避免认证冷查并发保护混入账号调度。主对照 5,120 次，另有预热 464 次及故障探针 130 次，合计 5,714 次；最大并发 128，无真实上游付费调用。

四轮正常流量均没有进入恢复等待，没有恢复等待/释放日志。时延存在机器负载及原有随机退避波动，这组短时测试不能证明所有生产负载下延迟完全一致。

异常另测：部分上游持续 503 时，128/128 成功，143 次上游调用，单请求最多 3 次，P95 785ms。首次选号遇到所有健康来源暂不可用约 2 秒：关闭恢复约 70ms 返回 503，开启恢复约 3.31 秒返回正常答案，说明首次请求的恢复仍有效。

定向单元测试比较了开关两种状态下的同一账号、同一并发限制、抢槽次数和 WaitPlan 截止时间；即使恢复队列已满，也不影响未发生异常的正常请求。还覆盖延迟一小时后首次失败才开始预算、不可恢复错误不激活、同轮不重置预算及 WebSocket 新轮回到正常调度。完整 config/handler/service 单元测试通过（约 0.7/50.4/237.3 秒），包含高级调度相关既有测试。
